# Contributing

Skim Reading Lens is GPL-3.0-only. Contributions should preserve the user's source text, keep activation understandable, and disclose actual data handling. The canonical development repository is [Aabdulnour/skim-reading-lens](https://github.com/Aabdulnour/skim-reading-lens).

## Start here

1. Fork or clone the public repository and read README.md, AGENTS.md, and docs/ARCHITECTURE.md.
2. Create a focused branch in your existing checkout and run npm test.
3. Use the hosted reading lab or npm start to inspect the interface.
4. Run npm run package, then load extension/ as an unpacked extension in a separate desktop Chrome test profile.
5. Keep changes focused on a concrete reading, accessibility, privacy, or reliability problem.

There are no npm packages to install for normal development. Python 3 builds the release artifacts. The separate lab's pinned camera runtime and models are bundled; see docs/GAZE.md for dependency maintenance. The public source does not need the maintainer's deployment credentials, Google account, or Jev key.

Claude Code reads CLAUDE.md, which refers to the same AGENTS.md guidance used by other coding agents. Keep work in one checkout and review its diff before opening a pull request.

## Development boundaries

- Extension runtime code must remain bundled and compatible with its Manifest V3 content security policy.
- Do not add analytics, remote page-text processing, camera capture, broad required website access, paid services, or an account requirement as an incidental change.
- A site becomes persistent only after an explicit user action and Chrome permission grant.
- Do not rewrite source paragraphs to install the highlight. Preserve original wording and surrounding context.
- Do not intercept typing shortcuts inside editable fields.
- Use textContent for untrusted text. Keep pasted or extracted HTML inert.
- Source content is data, not instructions for application behavior or provider calls.
- Treat webcam input as an estimate. Keep the validation gate and cleanup behavior.
- Do not present scripted attention as real gaze or selected claims as verified facts.
- Do not include private deployment metadata, personal test conversations, or repository credentials in a patch or release archive.
- Keep website and extension behavior distinct in documentation. The current extension remains pointer-only.

## Checks for a pull request or patch

Run npm test for behavior changes. Add a regression case for a substantive bug or boundary condition. Verify the affected user flow in Chrome when unit tests cannot establish it. Describe what was tested and what remains untested.

Run npm run release only when preparing artifacts. If you add an extension runtime file, update the explicit allowlist in scripts/package.py. If you add a root source document needed by contributors, include it in the source export allowlist. Keep package.json and extension/manifest.json versions aligned for releases.

Edit the local reader's source in dist/. The extension/reader/ directory is generated by npm run package and should not receive independent changes. Test the generated reader when its source changes.

Open a [bug report or feature proposal](https://github.com/Aabdulnour/skim-reading-lens/issues/new/choose) using the provided templates. Submit focused pull requests to main with the problem, resulting behavior, test evidence, and remaining limits. Routine support is also available at [justfornow609@gmail.com](mailto:justfornow609@gmail.com). There is no guaranteed response time.

No GitHub Actions workflows are configured. Run the local checks and include the result in the pull request. Add CI, telemetry, a paid service, or a deployment integration only as an explicit product decision with its cost and permission implications reviewed.

## Useful first contributions

- Reproduce a lens or reader failure with a short synthetic page and fix the smallest affected behavior.
- Record a complete installed-Chrome flow using the checklist in docs/RELEASE.md, including permission denial and removal.
- Improve keyboard access or an unclear first-use message without adding another required setup step.
- Measure webcam calibration and drift on a real device using docs/GAZE.md. Report measured results and failed checks as carefully as successful ones.

A new eye-tracking integration or Mac companion should begin with a small design proposal explaining the input, calibration, coordinate mapping, camera lifecycle, packaging, and fallback behavior. Do not replace a measured accuracy gate with an optimistic success message.

## Privacy in examples and reports

Use synthetic sample pages. Remove private URLs, conversation text, account names, screenshots with personal information, access tokens, and API keys. A useful report can usually identify a site family and a short artificial paragraph without exposing a real conversation.

Security-sensitive reports should follow SECURITY.md.
