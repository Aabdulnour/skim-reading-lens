# Working on Skim Reading Lens

## Project and scope

The canonical development repository is https://github.com/Aabdulnour/skim-reading-lens. Use the existing checkout and preserve unrelated changes. The public website is https://skim-attention-lab-anthony.aabdulnour01.chatgpt.site. Its deployment checkout is a separate publishing surface, not an alternative development history to expose publicly.

Skim has three distinct surfaces:

- A Manifest V3 Chrome extension with a local pointer lens, optional remembered sites, and a local reader.
- A public reading lab with optional webcam estimates, calibration, and a held-out validation gate.
- An optional loopback development server that can ask TypeSafe Jev to select an existing sentence after explicit opt-in.

The current extension does not track eyes over arbitrary webpages. The project does not contain a native Mac app. Keep those limits clear when describing a change.

Read README.md, docs/ARCHITECTURE.md, and docs/VALIDATION.md before making substantial changes. Use docs/GAZE.md for camera work and docs/RELEASE.md for release work. CLAUDE.md points to this file so project instructions have one home.

## Commands

Requires Node.js 20+ and Python 3. Normal development does not require npm dependency installation.

```bash
npm test
npm start
npm run package
npm run release:check
```

`npm start` serves the site at http://127.0.0.1:4173. `npm run release` runs the tests, creates the downloadable artifacts, and checks them. `npm run release:check -- --submission` also checks the configured public contact. These checks cannot establish Google account verification or store approval.

Load `extension/` through Chrome's **Load unpacked** control after packaging. Reload the extension card and refresh the test page after a runtime edit. The generated store ZIP has manifest.json at its root; the tester ZIP has a containing folder.

## Source ownership and packaging

- Edit the lab in dist/. Edit the on-page extension and its UI in extension/.
- extension/reader/ is generated by scripts/package.py from the lab. Change the source and regenerate it instead of maintaining divergent copies.
- scripts/package.py has explicit runtime and root-source allowlists. Update the relevant allowlist when adding a required file.
- Keep package.json and extension/manifest.json versions aligned for releases. Rebuild after any source, documentation, or listing-image change.
- Keep third-party runtime/model assets pinned and their provenance and licenses documented. Use the documented dependency-maintenance process, not an unversioned CDN URL.
- Keep .openai/ hosting metadata, Git history exports, secrets, private examples, and local test artifacts out of public source bundles.
- Avoid creating parallel state or handoff documents. Record evidence in docs/VALIDATION.md and release changes in CHANGELOG.md.

## Behavior and data boundaries

- Preserve original source wording and context. The overlay uses highlight ranges instead of replacing or wrapping the page's text.
- Treat text from pages and pasted input as data. Use textContent for untrusted text and retain the extraction bounds.
- Keep the extension runtime bundled and compatible with its Manifest V3 CSP. Remote executable code is not part of the extension.
- Persistent activation requires a deliberate site choice and the corresponding Chrome permission grant. Preserve denial fallback, pause, forgetting, and permission-revocation behavior.
- Camera use is explicit and optional. Preserve consent, calibration, held-out validation, and track shutdown on cancellation or loss of the active session. Never label a scripted tour as real gaze.
- Jev credentials stay in the local server environment. Keep cloud opt-in, bounded requests, permitted sentence IDs, safe fallback, and existing spending limits.
- Do not add analytics, external page-text processing, new required permissions, an account requirement, paid infrastructure, or a native companion as incidental changes. Treat them as explicit product changes within the user's current request.
- Keep typing shortcuts and editable fields usable. Test focus and keyboard behavior when changing controls.

## Verification and communication

Run existing checks relevant to the change. Add a targeted regression test for a substantive bug or new boundary, rather than duplicating implementation details in tests. Documentation-only edits need accurate links, current statements, and package inclusion; they do not require unrelated runtime changes.

Browser fixtures and mocked cameras do not prove installed Chrome behavior or human gaze accuracy. For those claims, record the actual browser/device, flow exercised, result, and remaining gaps in docs/VALIDATION.md. Keep implemented, tested, pushed, deployed, store-approved, and useful-to-testers as separate claims.

Use plain language and no em dash characters in authored prose. Explain the concrete problem, resulting behavior, verification, and any material limitation. Do not describe a passing build as proof of faster reading or better comprehension.
